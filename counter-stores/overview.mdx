By default, ThrottlingTroll tracks request counts using `MemoryCacheCounterStore`, an in-process store backed by the local memory cache. This works perfectly for single-instance deployments and local development, but in a horizontally-scaled environment each instance maintains its own independent counters — so a client can exceed your intended limit by hitting different pods or servers. To enforce consistent rate limits across all instances, you need a **distributed counter store**.

## Available Counter Stores

| Store | NuGet Package | Best for |
|---|---|---|
| `MemoryCacheCounterStore` | Built-in | Single-instance, dev/test |
| `RedisCounterStore` | `ThrottlingTroll.CounterStores.Redis` | High-throughput production |
| `AzureTableCounterStore` | `ThrottlingTroll.CounterStores.AzureTable` | Azure-hosted services |
| `DistributedCacheCounterStore` | `ThrottlingTroll.CounterStores.DistributedCache` | Any `IDistributedCache` implementation |
| `EfCoreCounterStore` | `ThrottlingTroll.CounterStores.EfCore` | SQL Server / any EF Core database |

## Registering a Counter Store

There are two ways to supply a counter store to ThrottlingTroll. Choose the approach that best fits your application's architecture.

### Option 1 — Inject via Dependency Injection (recommended)

Registering the store as a singleton in the DI container lets you share a single instance across the entire application — including multiple ThrottlingTroll middleware registrations and `HttpClient` handlers.

```csharp
using StackExchange.Redis;
using ThrottlingTroll;

services.AddSingleton<ICounterStore>(
    new RedisCounterStore(ConnectionMultiplexer.Connect("localhost:6379"))
);
```

ThrottlingTroll automatically resolves `ICounterStore` from the container when the middleware is initialised.

### Option 2 — Set directly on `ThrottlingTrollOptions`

You can also assign the counter store inline when calling `UseThrottlingTroll`:

```csharp
app.UseThrottlingTroll(options =>
{
    options.CounterStore = new RedisCounterStore(
        ConnectionMultiplexer.Connect("localhost:6379")
    );
});
```

This is convenient for quick setups, but creates a store instance that is not shared with other middleware registrations.

## Namespacing Counters with `UniqueName`

When multiple services — or multiple ThrottlingTroll configurations in the same service — write counters to the same shared store, their counter keys can collide. Use the `UniqueName` property on `ThrottlingTrollConfig` to add a prefix to every counter key generated by that configuration:

```csharp
app.UseThrottlingTroll(options =>
{
    options.Config = new ThrottlingTrollConfig
    {
        UniqueName = "my-service-v2",
        Rules = [ /* ... */ ]
    };
});
```

Setting a unique name per service ensures counters are isolated even when the underlying storage is shared.

## The `ICounterStore` Interface

All counter stores implement the same interface, which means you can build your own store by implementing three methods:

```csharp
public interface ICounterStore
{
    /// <summary>Gets a counter by its key.</summary>
    Task<long> GetAsync(string key, IHttpRequestProxy request);

    /// <summary>
    /// Atomically increments and returns the counter.
    /// Also sets or extends the counter's TTL.
    /// </summary>
    Task<long> IncrementAndGetAsync(
        string key,
        long cost,
        CounterTtl ttl,
        IHttpRequestProxy request);

    /// <summary>Decrements a counter by its key.</summary>
    Task DecrementAsync(string key, long cost, IHttpRequestProxy request);

    /// <summary>Logging delegate set by ThrottlingTroll — do not override.</summary>
    Action<LogLevel, string> Log { get; set; }
}
```

The `IHttpRequestProxy` parameter is passed for context (e.g. for logging or custom partitioning) but most built-in stores do not use it.

<Note>
  The `SemaphoreRateLimitMethod` (concurrency limiter) relies on `DecrementAsync` to release a slot when a request completes. When used across multiple instances you **must** use a distributed counter store; otherwise each instance tracks its own concurrency window. With `RedisCounterStore` and a `PermitLimit` of `1`, ThrottlingTroll acts as a distributed lock.
</Note>

<Tip>
  ThrottlingTroll emits OpenTelemetry metrics that reflect rate limit pressure in real time. Consider wiring these metrics into your autoscaler (e.g. KEDA or Azure Monitor autoscale) so that your infrastructure scales out before clients start hitting `429 Too Many Requests` responses.
</Tip>
